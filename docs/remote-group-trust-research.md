# 被控端该信谁：设备组在 Mac 上的增删规则怎么收敛（研究）

2026-11-17。起因是资历规则（`docs/remote-device-group-design.md` §18）落地后还留着一处：正常组员替攻击者的设备担保后成了它的「上游」，攻击者的设备可以撤这台组员。本文回答三件事：这处到底影响多大、为什么补了四轮还有洞、往后怎么改。**只是研究，没有改代码。**

## 结论

1. **这处洞的触及面很窄**：只影响**没进设备组的 Mac**，攻击者要先从一台被偷的组员设备里**取出长期密钥**（只会点界面做不到），效果是把替它担保的那一台从这台 Mac 上挤掉，别的更早的组员照样能把攻击者撤掉。不建议为它单独再补一条规则。
2. **根因不在某条规则写得不严**：没进组的 Mac 手里只有一张「谁替谁担保过」的图，它是设备组签名名单的影子。两台都被信任的设备互相说「对方丢了」，只凭 Mac 手里的东西分不出谁说的是真的。四轮补丁（连带、留请求者、资历、请求者被撤后的补问）都是在猜，每一轮都带出新的边角。
3. **进了组的 Mac 没有这个问题**：它自己读签名名单，每一轮按名单重算主控端，被错撤的组员下一轮就记回来。
4. **推荐方向**：不再给影子加规则，分三步：
   - 现在：移除 / 加入 / 离开前要求本机验证（面容 ID、触控 ID 或密码）。挡的是更现实的情况：有人拿到一台解锁的设备，在界面上把你的设备全移除。
   - 现在：界面上提示把自己的 Mac 加进设备组。进组的 Mac 不走这套猜的规则。
   - 排期：没进组的 Mac 改成「见证者」，用同一套名单算法验签名记录，手动配对的那台是锚点、不能被远程移除。做完可以删掉被控端这一摞启发式规则。
5. **要你定的两件事**在最后一节。

## 1. 这处洞要什么条件

复述：被偷的 X 把攻击者的 Y 弄进设备组 → 正常组员 M 照「组员替彼此向 Mac 开通」替 Y 向 Mac 担保 → 在这台 Mac 上 M 成了 Y 的上游 → Y 可以撤 M（撤上游一律允许）；Y 若是 M 在这台 Mac 上担保的第一台，留下的是 Y。

按代码读下来，成立要同时满足：

| 条件 | 依据 |
| --- | --- |
| 攻击者手里有一台组员设备的**长期密钥**，不只是能点它的界面 | 加入设备组要往 iCloud 钥匙串写 `join` 记录，Y 不在你的 Apple ID 里写不了；快通道只和钥匙串名册里登记过的设备握手。只会点界面的人加不进 Y。拿到 X 的身份私钥和签名私钥的人可以以 X 的身份进快通道，塞一条 X 签的 `admit(Y)`；正常组员认下后会补签并写进钥匙串。**这一条是读代码得出的，没有写测试验证。** |
| 那台 Mac **没进设备组** | 进了组的 Mac 每轮按签名名单重算（`RemoteDeviceGroup+LocalHost.swift` 的 `syncLocalHost`）：M 还是组员，被撤后下一轮就由这台 Mac 自己记回来（撤销不拉黑）。 |
| M 是第一个替 Y 向这台 Mac 担保的 | 否则留下的不是 Y。 |

效果的上限：M 和 M 之后在这台 Mac 上担保的设备被挤掉；Y 留下。恢复：任何一台比 Y 早、没被挤掉的组员撤 Y（资历允许），或者到 Mac 上撤。Y 撤不了不是它上游的、比它早的组员。

对比同一个攻击者本来就有的能力：X 的密钥在他手里，X 在被移除之前本来就能控制它能连的每一台 Mac。这处洞多给他的是「在一台没进组的 Mac 上，多挤掉一台正常设备」。

**判断：严重程度低。** 没进组的 Mac 实际只有两种：你自己的、还没点「加入」的 Mac（加进去就没事）；别人的 Mac（不同 Apple ID，进不了你的组）。

## 2. 更现实的威胁在别处

把攻击者按能力分三档：

| 档 | 能做什么 | 现在挡住了吗 |
| --- | --- | --- |
| 拿到一台**解锁的**组员设备，只会点界面 | 远程控制它能连的 Mac；在「我的设备」里把别的设备一台台移除（组里任何组员都能移除任何组员，谁先动手谁算数）；加不进新设备 | iOS 上应用锁默认关（`AppLockPreference.defaultValue`，Mac 默认开）。应用锁关着时全都挡不住 |
| 还能取出那台设备的密钥 | 上面全部，加上伪造 `admit` / `remove`、替任意钥匙向 Mac 担保 | 被移除之前挡不住；移除之后签名不再算数 |
| 只有你的 Apple ID（没有组员设备） | 读写钥匙串名册：删记录、让验证码作废 | 加不进组（要组员输验证码，CPace），拿不到 Mac |

第一档比第一节那处洞常见得多，而且现在的名单算法对它没有防线：`RemoteGroupMembership.resolve` 里**任何组员都能移除任何组员**，按记录里写的时间先后处理，先被移除的那台之后签的不算。被偷的设备抢先把别的都移除，你的设备就都出组了（可以另起一组，但手动配对在各台 Mac 上的那台被偷设备还在）。

## 3. 为什么补了四轮还有洞

没进组的 Mac 记的是：信任表（设备 ID、远控公钥、配对时间）加担保记录（谁替谁担保、组号）。它**不认识设备组的签名**，不知道谁被谁加进组、谁被谁移除。于是：

| 轮 | 问题 | 补法 | 带出的新问题 |
| --- | --- | --- | --- |
| G3 | 同组撤销拉黑，取消报告后回不来 | 同组撤销不拉黑 | 被撤的设备能被它担保过的设备担保回来 |
| G3 补 | 同上 | 撤一台连带撤它担保的，留请求者 | 攻击者抢先撤，正常组员全被带走 |
| 资历 | 同上 | 只能撤上游或更晚的；撤上游留最早的 | 请求者自己被撤，要别人补问；「上游」被自动担保利用 |
| 配套 | 请求者被撤后没人管 | `requesterRevoked`、停着的 Mac、`not-trusted` 也补问 | 补问次数按组员数平方涨；新旧版本混用时弹审批框 |

§15、§18 的「仍然不严的地方」加起来有十几条。它们的共同点：**Mac 在用「担保图 + 配对时间」猜设备组里发生了什么。**

更根本的一点：即使 Mac 拿到了全部签名记录，也有一种情况分不出来——两台它都认的组员各签一条「移除对方」。「正常的 M 移除被偷的 X」和「被偷的 X 移除正常的 M」在记录上是对称的。要分出来只能引入不对称：

- **谁先**（现在名单算法用的）：对抢先的一方有利；
- **资历 / 上游**（§18）：对早加入的有利，但「上游」可以被自动担保制造出来，较晚的正常设备反而撤不了较早的被偷设备；
- **锚点**：Mac 主人当面批准过的那台说了算；
- **人**：到 Mac 上处理，或者操作前验证是不是本人。

前两种是在记录里找不对称，找不到可靠的。后两种是从记录之外拿：Mac 主人当面做过的决定，和「此刻拿着设备的是不是本人」。

## 4. 几种改法

### A. 再补一条：让「上游」取设备组里的添加者，不取替它担保的那台

担保请求多带一个「它是谁加进组的」，Mac 按这个算上游。Y 的上游是 X，不是 M。

- 好处：改动小（消息 50 加一个可选字段）。
- 问题：这是担保者口头说的，没有签名。X 的密钥在攻击者手里时，X 替 Y 担保可以谎称「Y 是 M 加的」。要挡谎话得限制「只能报自己或自己的上游」，那么 M 和 X 是平辈时 M 说的真话也不被采信，洞还在。要让它可验证就得带上签名的 `admit`、让 Mac 认签名钥匙——那是 C。
- 评价：第五条启发式，不建议。

### B. 只认锚点（星形）

在没进组的 Mac 上，**只有手动配对的设备（锚点）能替别的设备担保、能撤它担保的**；被担保进来的设备没有任何权力（除了撤自己）。

- 好处：被控端的规则缩到二十行以内，`family` 之外的连带、留谁、改挂、资历、`requesterRevoked`、停着的 Mac、`not-trusted` 补问都可以删。被偷的非锚点设备在这台 Mac 上什么都改不了；攻击者的 Y 即使被锚点自动担保进来也没有权力，锚点随时能撤。
- 代价一：**锚点丢了（或被偷）只能到 Mac 上撤**。现在别的组员可以远程撤它。
- 代价二：**换手机后要到每台没进组的 Mac 上重新配对**。旧手机是锚点，新手机进了设备组，但旧手机不在了，没人能替新手机担保（现在 iPad 可以替它担保）。
- 代价三：锚点连不上那台 Mac 时，新设备等着，移除也等着。
- 评价：最省事，但换手机那一条是明显的退步。

### C. 没进组的 Mac 当见证者，验签名记录（推荐的终点）

没进组的 Mac 不再记担保图，改成**用同一套名单算法旁观这个组**：

- **锚点**：Mac 主人手动配对的设备。它在已认证的连接上报自己的签名公钥和加入记录，Mac 以它为起点建一份名单状态（`RemoteGroupLocalState`，Mac 自己不签名）。
- **证据**：组员连上来时把组里签过名的 `admit` / `remove` 送给 Mac（新消息，原样的名册记录，几 KB）。Mac 只做并集，收过的不会被撤回。
- **算**：Mac 的 App 跑 `RemoteGroupMembership.resolve`，得出此刻的组员；再用进组的 Mac 已有的那套「按名单记 / 撤主控端」（`syncLocalHost`、`groupAddController` / `groupDropController`）落到信任表上。
- **不对称取锚点**：手动配对的设备不因为组里的记录被撤，只有 Mac 主人或它自己能撤。锚点被移出它所在的组时，靠它进来的设备一起撤，锚点自己留着。

效果：

| 情况 | 现在 | 见证者 |
| --- | --- | --- |
| 被偷的非锚点 X 抢先移除正常组员 | 看资历，有边角 | 在 Mac 上生效（X 还是组员），锚点移除 X 后全部恢复；X 挤不掉锚点 |
| 攻击者的 Y 撤替它担保的 M | 能 | 没有「上游」这回事；Y 要移除 M 得签 `remove`，全组可见，和上一行同样处理 |
| 换手机（旧手机是锚点） | iPad 替新手机担保 | iPad 签的 `admit` 链到锚点，Mac 认，不用重新配对 |
| 锚点连不上 | 别的组员照样能开通、能撤 | 同左（任何组员都能送证据） |
| 锚点被偷 | 别的组员可以远程撤它（有抢先的问题） | 要到 Mac 上撤 |
| 请求者自己被撤、补问、停着的 Mac | 有 | 没有：撤谁由签名记录决定，不由谁发的请求决定 |

代价：

- 工作量大：新消息一对（现在排到 54 / 55）、远控进程到 App 的转发（XPC 只加）、App 里每个锚点一份名单状态与证据的存储、和旧的 50–53 并存一段时间（老版本的设备和 Mac 还在用）。粗估一到两周，含对抗测试。
- 别人的 Mac 会看到你设备组的名册记录（设备名、机型、公钥）。现在担保时它已经能看到被担保设备的名字，范围变大了。可以只送和这台 Mac 有关的那条链。
- 锚点被偷要到 Mac 上处理，比现在少一条远程的路。这是有意的：那条路正是分不清谁说真话的地方。

### D. 操作前验证本人（和 A / B / C 都不冲突）

移除、输入验证码把新设备加进组、离开设备组之前，调一次本机验证（iOS 面容 ID / 密码，Mac 触控 ID / 密码；`BiometricAuthenticator` 已有）。

- 挡第二节的第一档：拿到解锁设备的人过不了验证，移除不了你的设备、加不进新设备。
- 不是密码学上的保证（密钥还在设备里），取得出密钥的人不受它约束。
- 工作量小：两端各一处入口，加测试。应用锁开着的人多验一次，可以在刚解锁的几分钟内免验。

### E. 让自己的 Mac 都进组

Mac 上「我的设备」显示「未加入」时给一句提示；配对一台同一 Apple ID 的 Mac 后提示把它加进组。进组的 Mac 按签名名单重算，第一节那处洞在它上面自己就好。

## 5. 推荐

| 步 | 做什么 | 理由 |
| --- | --- | --- |
| 1 | D：移除 / 加入 / 离开前验证本人（**已做**，`docs/remote-device-group-design.md` §19） | 最便宜，挡的是最常见的一档 |
| 2 | E：提示把自己的 Mac 加进组（**已做**，同上 §19） | 让尽量多的 Mac 走签名名单 |
| 3 | 第一节那处洞记为已知限制，不补 A | 触及面窄，再补一条启发式只会多一个边角 |
| 4 | C：见证者，排期做 | 唯一能把被控端那一摞规则删掉的路 |

不选 B：换手机后要到每台没进组的 Mac 上重新配对，日常就会碰到。

做完 C 之后可以删的（现有代码）：`RemoteVouchPolicy` 的 `cascade` / `reanchor` / `survivor` / `ancestors` / 资历判断，`RemoteHostServer.removeVouchedSubtree`，组员一侧的 `requesterRevoked`、`pausedHosts`、`not-trusted` 补问、「重新算起」。担保（消息 50 / 51）留给老版本和「不在设备组里的已配对设备担保」。

## 6. 要你定的

1. **锚点被偷时只能到 Mac 上撤**（C 的规则）。现在别的组员可以远程撤它，但这正是分不清谁说真话的地方。接受这一条，被控端才能收敛。推荐接受。
2. **C 排不排期。** 它不解决眼下用得着的问题（你的三台设备里两台 Mac 都进组了），是为了把逻辑理顺、以后少出边角。不排的话，建议只做 1、2 两步，把第一节那处记为已知限制。
